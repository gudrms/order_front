# ADR-0003. 배달 운영을 테스트 매장에서 실 김포점으로 이전

- 상태: **채택됨**
- 날짜: 2026-09-21
- 관련: 운영 DB 직접 변경 (코드 변경 없음), `apps/backend/src/modules/menus/menus.service.ts`

## 배경

정식 출시 이후 점검에서, **배달이 켜진 유일한 매장이 테스트용으로 만든 매장**이었다.

| | 실 김포점 | 배달 켜진 매장 |
|---|---|---|
| id | `1e9889b1-628b-…` | `test-admin-direct-store` |
| storeType / branchId | `tacomolle` / `gimpo` | `test` / `admin-direct-test` |
| 주소 | 정상 | **전화번호가 들어가 있음** |
| 좌표 | 있음 | 없음 |
| 메뉴 | 29건 (공개 0건) | 6건 (공개 5건) |
| 배달 | 꺼짐 | **켜짐** |

`storeType`/`branchId`/`id`는 고객이 보는 URL에 그대로 들어간다
(`delivery.tacomole.kr/store/test-admin-direct-store`, 테이블오더 QR `.../test/admin-direct-test/table/1`).
코드가 `test` 값으로 분기하는 곳은 없어 **동작은 정상**이었고, 노출만 문제였다.

실 김포점의 메뉴 29건이 공개 0건이던 이유는 따로 있었다. 매장이 `TOSS_POS` 모드인데
29건 전부 `tossMenuCode`가 비어 있어 `menus.service`의 `where.tossMenuCode = { not: null }` 필터에 전부 걸렸다.
**Toss POS 동기화가 한 번도 성공한 적이 없는 상태**였다.

## 결정

배달 운영을 **실 김포점으로 옮긴다.** 단일 트랜잭션으로 실행했다.

1. 실 김포점의 예전 메뉴 29건 삭제 (사용자 확인: 예전 데이터)
2. 테스트 매장의 카테고리 11건·메뉴 6건을 실 김포점으로 이전
3. 실 김포점을 `ADMIN_DIRECT`로 전환 (Toss POS는 당분간 쓰지 않기로 함)
4. 배달 ON + 배달비 3,000원 / 최소 주문금액 10,000원
5. 테스트 매장은 배달 OFF + `isActive=false`

이후 네이버 플레이스 메뉴판을 기준으로 실제 메뉴 33건을 등록했다.

**대안이었던 "테스트 매장을 그대로 승격"**(주소만 수정)은 5분이면 끝나지만
`test-admin-direct-store` URL이 영구히 남는다. 정식 출시 직후가 URL을 바꾸는 가장 싼 시점이라 이전을 택했다.

## 결과

**얻은 것**
- 고객 URL이 `tacomolle/gimpo`로 정상화됐다.
- 매장 주소·좌표가 정상이라 브랜드 사이트 지도와 거리 계산이 맞는다.
- 브랜드 사이트에 김포점이 두 번(하나는 주소 자리에 전화번호) 뜨던 것이 해소됐다. 공개 매장 8건 → 7건.

**잃은 것 / 남은 것**
- 테스트 매장에 **주문 이력이 남아 있다.** `OrderItem`이 메뉴를 FK로 참조하지 않고
  `menuName`/`menuPrice`를 스냅샷하므로 이력 자체는 깨지지 않았지만, 통계에서 두 매장으로 갈린다.
- 테스트 매장의 `address`에 전화번호가 그대로 남아 있다. 비공개라 고객 영향은 없다.
- **`Toss POS` 모드로 되돌리려면** 동기화를 먼저 성공시켜야 한다. 모드만 바꾸면 메뉴가 통째로 사라진다.

**얻은 교훈**

`/stores/:id/menus`가 0건을 반환한다고 메뉴가 없는 게 아니었다. 이 API는
`isActive`·`isHidden`·`menuManagementMode`로 필터링한다. **DB를 봐야 실제 상태를 알 수 있다.**
이전 SQL의 사전 확인(`대상 매장에 이미 메뉴가 N건 있으면 중단`)이 실제로 걸려서,
29건 위에 6건을 덮어쓰는 사고를 막았다. **운영 DB 변경에는 사전 확인을 반드시 넣는다.**
