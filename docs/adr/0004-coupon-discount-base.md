# ADR-0004. 쿠폰 할인은 상품 금액 기준, 한도는 발급 수 기준

- 상태: **채택됨**
- 날짜: 2026-09-21 (할인 기준은 2026-09-20 확정)
- 관련: `apps/backend/src/modules/coupons/coupons.service.ts`, `apps/backend/src/modules/orders/delivery-order.service.ts`

## 배경

쿠폰 기능을 실제로 운영에 올리기 전에 두 가지가 정해지지 않았거나 잘못돼 있었다.

**1. 할인 기준.** 쿠폰 할인을 배달비까지 포함한 총액에 적용하면, 배달비가 실비인데도
쿠폰이 그 실비를 갉아먹는다. 최소 주문금액 판정 기준도 모호했다.

**2. 발급 한도.** `maxUses`는 스키마상 "총 발급 한도"인데 코드는 `usedCount`(실제 결제에 사용된 수)를 검사했다.
발급만 하고 안 쓰면 카운트가 올라가지 않아 **한도를 훨씬 넘겨 발급될 수 있었다.**
게다가 관리자 직접 발급 경로는 한도 검사를 아예 하지 않았고, 동일 고객 재발급은
DB 유니크 제약에 걸려 500으로 나갔다.

## 결정

**1. 할인과 최소 주문금액 모두 배달비를 제외한 상품 금액 기준으로 계산한다.**

```
finalAmount = (상품금액 + 배달비) - 할인액     // 할인액은 상품금액 기준으로 산출
```

할인액은 상품 금액으로 계산하지만 **최종 결제액에서 통째로 차감**된다.
따라서 "배달비 3,000원 + 정액 3,000원 쿠폰"과 "배달비 0원"은 고객이 내는 돈이 정확히 같다.
**배달비 상쇄 쿠폰을 위해 별도 쿠폰 타입을 만들 필요가 없다.**

**2. 한도는 발급된 `UserCoupon` 수를 기준으로 본다.** 관리자 직접 발급과 프로모 코드 등록이
공통 `assertIssuable()`을 거치게 통합했다. 목록 API는 `_count`로 `issuedCount`를 함께 내려주고,
화면에는 `발급 n장 / 한도 m장`과 `사용 n장`을 **분리해서** 표기한다.

**3. 정액(FIXED_AMOUNT)을 기본으로 권장한다.** 비용이 예측 가능하고 고객이 바로 이해한다.
정률은 상한(`maxDiscountAmount`) 입력을 필수로 막았다.

## 결과

**얻은 것**
- 배달비가 할인에 잠식되지 않는다.
- 한도가 예산 통제 수단으로 실제 동작한다.
- 중복 프로모 코드·중복 발급·한도 초과가 모두 500이 아닌 400과 한글 안내로 나간다.

**의도적으로 남긴 것**
- **동시 요청이 겹치면 한도를 1~2장 넘길 수 있다.** 발급 수를 세고 나서 생성하는 사이에 틈이 있다.
  예산 통제 목적에는 충분하다고 보고 잠금을 두지 않았다. 엄격히 막으려면
  발급 수 컬럼 + 조건부 증가가 필요하다. 이 판단 근거는 `assertIssuable` 주석에도 적어두었다.

**운영 기준**
- 쿠폰 최소 주문금액은 **매장 최소 주문금액보다 높게** 잡아야 역마진이 나지 않는다.
  현재 김포점 최소 주문금액이 10,000원이므로 쿠폰은 15,000원 이상을 권장한다.
- 상시 혜택은 쿠폰이 아니라 `freeDeliveryThreshold`(N원 이상 무료배달)로 주는 것이 맞다.
  발급·한도 관리가 필요 없고 객단가를 끌어올린다. 쿠폰은 신규 유입 1회성으로 쓴다.
- 자사앱 가격을 배달 플랫폼보다 싸게 가져갈 때는 **플랫폼 계약서의 최혜대우 조항을 확인할 것.**
