# ADR-0005. 메시지 큐로 pgmq를 쓴다

- 상태: **채택됨**
- 날짜: 2026-05-01 (기록 정리 2026-09-22)
- 관련: `apps/backend/src/modules/queue/`, `.github/workflows/` cron, `docs/architecture.md` 「메시지 큐 (pgmq)」

## 배경

결제가 끝난 뒤 두 가지가 이어져야 한다.

- 주문을 **POS로 전송**
- 점주·고객에게 **FCM 알림 발송**

둘 다 외부 시스템이라 실패하거나 느릴 수 있다. 결제 트랜잭션 안에서 동기로 처리하면
POS가 죽었을 때 결제까지 같이 실패한다. 그래서 큐로 분리해야 했다.

문제는 **상시 실행되는 consumer를 둘 곳이 없다**는 점이었다. 백엔드가 Vercel Serverless라
요청이 없으면 프로세스가 살아 있지 않다. 워커를 돌리려면 별도 서버가 필요하다.

## 결정

**pgmq**(PostgreSQL 확장)를 쓴다. 이미 쓰는 Supabase DB 위에서 동작하므로 **인프라가 늘지 않는다.**

consumer는 상시 실행 대신 **주기적으로 깨우는** 방식으로 돌린다.

- GitHub Actions cron이 5분마다 `/queue/process-once`를 호출
- 백엔드가 메시지를 publish한 직후에도 Vercel background work(`waitUntil`)로 같은 엔드포인트를 깨운다
  (2026-05-22 추가 — cron만 기다리면 `order.paid` → `pos.send_order` → `notification.send`가
  단계마다 최대 5분씩 밀려 체감 지연이 훨씬 커진다)
- cron은 제거하지 않고 **wake-up 누락·일시 실패·backlog 회수용 fail-safe**로 남긴다

**검토했다가 접은 것**

| 대안 | 접은 이유 |
|---|---|
| Redis + BullMQ | Redis 인스턴스를 따로 띄워야 하고, 워커 상시 실행 문제는 그대로 남는다 |
| SQS 등 관리형 MQ | 외부 의존과 비용이 늘고, 7개 매장 규모에 과하다 |
| 결제 트랜잭션 안에서 동기 처리 | POS 장애가 결제 실패로 번진다 |

## 결과

**얻은 것**
- 추가 인프라 0. DB 하나로 큐까지 해결한다.
- POS·알림 실패가 결제를 건드리지 않는다.
- 큐 상태를 SQL로 바로 볼 수 있어 운영 조회가 쉽다(관리자 `/operations`).

**잃은 것 / 감수한 것**
- **처리 지연이 깨우기 주기에 묶인다.** wake-up이 붙어 평시에는 즉시에 가깝지만,
  wake-up이 누락되면 최대 cron 주기(5분)까지 밀린다.
- 처리량 한계가 DB에 묶인다. 지금 규모에서는 문제가 아니지만, 주문량이 크게 늘면
  큐 폴링이 DB 부하로 잡힐 수 있다.
- pgmq는 전용 MQ만큼 기능(지연 메시지, 우선순위, DLQ 정교화)이 풍부하지 않다.

**되돌리는 방법**

상시 워커를 둘 수 있는 환경(별도 서버·컨테이너)이 생기면 그때 전용 MQ를 재검토한다.
그전까지는 **깨우기 주기를 줄이는 쪽**이 비용 대비 효과가 크다.
publish 직후 wake-up이 이미 그 방향의 조치다.

**미검증으로 남은 것**

실제 결제부터 POS·알림까지의 지연은 운영 env(`BACKEND_QUEUE_PROCESS_URL`) 반영 후
계측하기로 했는데 아직 하지 않았다. checkList.md에 열려 있다.
